# x86-64 on the quantum machine

The third front end on the shared core (`qcpu/core.py`), after AArch64 and RISC-V.

| file | role |
|---|---|
| `qcpu/x86.py` | instruction table, byte decoder, static check, and a W-bit model of every instruction |
| `qcpu/x86_machine.py` | the circuit: the same decode and the same model, with gates |
| `qcpu/x86_reference.py` | CPU reference (Unicorn) with the per-instruction model check |
| `qcpu/loader.py` | ELF x86-64 relocations and the output stub (`docs/output_stub_x86.s`) |
| `tests/test_x86.py` | tests |

## What is different from AArch64 and RISC-V

| | AArch64 / RISC-V | x86-64 |
|---|---|---|
| instruction length | always 4 bytes | 1 to 15 bytes |
| program memory | 32-qubit words | 8-qubit bytes |
| program counter | counts instructions | counts bytes |
| operands | registers, one small immediate | register or memory in almost every instruction |
| result | separate destination register | overwrites the first operand |
| calls | return address in a register | return address pushed on the stack |
| flags | NZCV, set by a few instructions (RISC-V: none) | ZF/SF/CF/OF, set by almost every instruction |
| register writes | whole register | also the low byte (AL, CL, ...) |

## One machine cycle

1. **Fetch.** An 11-byte window at the PC. Program memory is divided into 16-byte blocks. A one-hot
   decode of the upper PC bits selects the block that holds the PC and the first 10 bytes of the next
   block; a byte shifter controlled by the low four PC bits aligns the window. 11 bytes hold the low
   16 bits of every field of any supported instruction, and W is at most 16.
2. **Normalise.** If the first byte is a REX prefix (0100xxxx), its four bits are kept and the window
   moves one byte; the same for the 0F escape byte. After this the opcode and the bytes that follow it
   are at fixed positions.
3. **Decode.** The kind table in `x86.py` lists exact (mask, value) patterns over the opcode and the
   byte after it (ModRM, whose `reg` field selects the operation in several opcodes), together with
   "0F escape present" and, where it matters, REX.W. The patterns are mutually exclusive. Then the
   ModRM / SIB layout: memory or register operand, SIB present, displacement size, immediate size,
   and from these the instruction length. A byte sequence that matches no pattern, or that breaks a
   validity rule (a byte-sized memory operand, AH/CH/DH/BH, LEA with a register, POP RSP), traps.
4. **Read.** Three register reads: the `reg` field, a "port" (the r/m register, the SIB base, or the
   register number in the opcode), and the SIB index. Effective address = base + index x scale +
   displacement (base may be absent, or the address of the next instruction for RIP-relative
   operands). One memory read: the r/m operand, or the top of the stack (POP, RET), or [RBP] (LEAVE).
5. **Execute.** Adder with flags, logic, barrel shifter, multiplier and divider from the core.
6. **Write.** One result goes to a register or to the memory operand. A byte result keeps the upper
   bits of its register. RDX gets the remainder of a division or the sign of RAX (CDQ / CQO). RSP
   changes by 8 for PUSH / POP / CALL / RET. A 64-bit store writes two cells: the value and its sign.
7. **Next PC.** PC + length, a relative branch, or an indirect target (register, memory, return
   address).

Copy-out, uncompute and commit are the core's, the same as for the other architectures.

## Implemented instructions

MOV (register, memory, immediate; 8, 32 and 64 bits), MOVSXD, MOVZX / MOVSX from a byte register, LEA,
ADD, OR, AND, SUB, XOR, CMP, TEST, NEG, NOT, INC, DEC, IMUL (two- and three-operand), CDQ / CQO, CDQE,
DIV, IDIV, SHL / SHR / SAR (by an immediate, by 1, by CL), SETcc, CMOVcc, Jcc (rel8, rel32), JMP (rel8,
rel32, register, memory), CALL (rel32, register, memory), RET, PUSH (register, memory, immediate), POP,
LEAVE, NOP (one byte and the 0F 1F forms), HLT (ends the run). Conditions: all except parity.

Not implemented (reported before the run; the circuit traps): 16-bit operand size and every other
prefix (66, 67, F2, F3, segment, LOCK), byte and word memory operands, AH/CH/DH/BH, ADC / SBB, rotates,
one-operand MUL / IMUL, XCHG, bit and string instructions, x87 / SSE / AVX, system instructions.

## Decisions

- **Registers are W bits** (8 to 16), as in the other machines. A 32-bit or 64-bit write replaces all
  W bits; a byte write replaces the low 8.
- **Flags** ZF, SF, CF, OF. Shifts write ZF and SF (if the count is not zero); the machine does not
  model CF and OF after a shift, nor any flag after IMUL, DIV and IDIV. It leaves those flags
  unchanged. The reference tracks which flags are unmodelled and reports a run that reads one.
- **DIV / IDIV** divide RAX; RDX must be its zero or sign extension (compilers emit `xor edx, edx` or
  `cdq` just before). The reference compares quotient and remainder with the CPU. Division by zero
  traps: the CPU raises an exception there.
- **Calls use the stack**, so every x86-64 run has data memory. The run starts like a call: RSP points
  at a return address that leads to an HLT in the last byte of program memory.
- **Compiler flags.** `-mno-sse` (integer code only), `-fno-pic` (absolute addressing),
  `-ffunction-sections` and `-falign-loops=1` so that the code contains no alignment padding:
  assemblers pad with prefixed multi-byte NOPs (`66 2e 0f 1f 84 ...`), which the machine does not
  implement. Padding between functions is never executed, but it would be listed as unsupported.
  For gcc also `-fcf-protection=none` (no ENDBR64) and `-falign-functions=1 -falign-jumps=1
  -falign-labels=1`.

## Model check

As for RISC-V: before each instruction the reference evaluates `x86.model()` on the W-bit encodings
of the CPU's registers, flags and memory; after the CPU has executed the instruction it reports an
issue if any register, flag, memory cell or the next PC differs in its low W bits, if a written value
does not fit the model at the width of the operation, or if a memory access is outside data memory,
unaligned, or not 4 or 8 bytes wide. A run without an issue is exact.

The tests split the soundness argument in two:

1. *The circuit implements the model.* `tests/test_x86.py` runs single cycles on random byte strings
   (random PC, registers, flags and memory) and requires the circuit to do exactly what
   `x86.decode()` + `x86.model()` say, including the trap for everything that is not a valid
   instruction. This covers encodings no assembler emits.
2. *The reference notices when the model and the CPU differ.* Boundary cases and random programs run
   on the CPU and on the circuit in lockstep; a difference that no issue explains fails the test.

## Known limits of the W-bit model on x86-64

All detected and reported, never returned as exact:

- A comparison whose difference does not fit W bits gives other SF and OF values than the CPU. The
  conditions built from them (`jl`, `jge`, ...) often still agree, but the flags are compared directly.
- A constant wider than W bits used as a mask (`test eax, 0x10000000`).
- Division by a constant, which compilers turn into a multiplication by a 32-bit constant
  (`digit_sum`), as on the other architectures.
- gcc `-O2` without SSE swaps two adjacent `int`s by packing both into one 64-bit word
  (`bubble_sort`). Such a word is not a sign-extended W-bit value.
- Unsigned division of a negative 32-bit value depends on the full register width, and a logical right
  shift of one gives a value that does not fit.

All machines select program slots and data cells with a binary decoder tree (`memory_select: tree`,
the default; the README section "Two ways to select memory" has the numbers for the original
comparator selection of the AArch64 and RISC-V machines). The x86-64 front end was written with the
tree from the start and has no comparator variant.

Most qubits are history: each cycle keeps the values it overwrote and, for data memory, one write
enable per cell and write port.
